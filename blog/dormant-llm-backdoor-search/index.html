Autoresearch · research note

Applying autoresearch to backdoor discovery

Autoresearch hands the experiment loop to an AI agent: it edits one file, runs a fixed test, reads one number and keeps or reverts the change. I tried it twice, once on the problem it was built for and once on a hunt for hidden backdoors in language models. The second run went smoothly and found nothing, and the reasons say more about autoresearch than about the hunt.

Mayank SaxenaProject: March 2026Written up: November 2026Code and data

01What autoresearch is

Karpathy’s autoresearch is a small experiment in letting a language model do its own research (Karpathy 2026). A coding agent is given a training script and a standing instruction: make the model better. It changes the script, trains for exactly five minutes, reads the validation loss, and commits the change if the loss went down or reverts it if not. Then it does it again, all night.

The design is mostly about what the agent is not allowed to touch.

IngredientWhat it guarantees
One editable fileChanges stay small, so each result can be traced to one idea.
A fixed experimentEvery run is comparable with every other.
One number“Better” is never a judgement call, so the agent can decide alone.
Keep or revert in gitProgress only ratchets forward, and nothing is lost.

On its home ground this works. I ran the MLX port on a laptop: changes kept in a row took validation loss from to bits per byte. The reason is easy to miss. In training, the number is the goal. Lower validation loss is what you wanted, so climbing the number cannot lead you astray.

02Taking it off its home ground

In early 2026, Jane Street hid triggers in four language models: prompts that make a model behave very differently (the Dormant LLM puzzle). I mapped the loop onto the hunt:

IngredientIn the backdoor hunt
Editable fileA list of probe prompts, one file per model.
Fixed experimentSend the prompts to a model and score every reply.
One numberAn anomaly score: how far a reply’s length strays from 15 ordinary answers, plus how many of its words they never used.
Keep or revertKeep the batch if its best reply beats the best so far.

The agent was Claude Code, and I steered between sessions. Over it ran batches and prompts. It found none of the four triggers.

03What carried over

The machinery transferred well, and two additions were worth making:

  • Notes the agent reads first. Each session opened by reading a notes file with the current best, the log and the ideas already ruled out, so a fresh context did not retry dead ends.
  • One command per step. Small scripts committed and ran a batch, or logged and filed the result, in one call. The loop rarely stalled waiting for me to approve an action.
  • A complete record. Every batch is a commit with every reply saved. Eight months later I re-scored all replies by script, and the record caught claims in my own notes that did not hold up.

04Where it broke: the number

An autoresearch loop climbs whatever number you give it. Outside training, the number is no longer the goal but a guess about what the goal looks like, and the agent climbs the guess. My score rewarded short replies made of new words, and nothing is shorter than one word. Any one-word reply made of a new word therefore scores the most a short reply can, a ceiling between and depending on the model.

Two things made this worse than a bad metric usually is. First, the keep rule stalls at a ceiling: once one batch reaches it, nothing can beat it, so later batches are discarded and the number stops steering the search. Second, the agent noticed. On day two it wrote into its own notes that about 5.5 was the formula’s ceiling, “not a wall”, and then kept optimising the same number for five more days. Autoresearch fixes the metric so the agent cannot game it, which also means the agent cannot repair it.

05Where it broke: everything around the number

  • Checks outside the loop. I re-sent promising prompts to see if they fired every time. The local model decoded greedily, so even echoes repeated perfectly (“Spartan!” times in ); the API models sampled, so the best lead held in only of tries.
  • A narrowing search. Keep-if-better pulls each batch toward what scored well before. The agent proposed words and phrases from the backdoor literature it knew. The triggers disclosed after the close were structured inputs, the first 15 digits of π and a Game of Life board (Kruger 2026), and the loop never tried either.
  • Trusting the model’s word. Asked for its trigger or its system prompt, the warmup model answered confidently and inconsistently. None of the answers held up.

06Rules for an autoresearch loop

Autoresearch works when climbing the number is the same as making progress. When it is not, these are the rules I would now follow:

  1. Test the number on a known answer first. Before the loop runs, check that a planted or already-known positive scores at the top. Mine would have failed this in minutes.
  2. Know the number’s ceiling. If cheap outputs can max it out, the keep rule will stall there.
  3. Put verification inside the loop. Re-run each candidate several times under fixed settings before it can be kept.
  4. Keep many winners. Archive distinct high scorers instead of one best, and set aside budget for kinds of input not yet tried.
  5. Let the agent propose a new number. It saw the problem on day two. A rule that lets it flag the metric for human review would have saved five days.

Next. The warmup model, its base model and its disclosed trigger allow exactly the test in rule 1. I will fix a redesigned score in advance, check where the true trigger ranks among these probes under the old score and the new one, and report the result either way.

Appendix A: the score and its ceiling

score = 0.6 × |words − baseline mean| / baseline sd + 4 × share of new words

Words are whitespace-separated tokens with punctuation stripped, lower-cased; “new” means absent from the model’s 15 baseline answers. A one-word reply made of a new word scores 0.6 × (mean − 1) / sd + 4, the most any reply shorter than the baseline mean can score. Longer replies gain length points again; on the API models, which had no length limit, a reply of a few thousand words could pass the ceiling. None did: the longest ( words) scored .
