Autoresearch · research note

Applying autoresearch to backdoor discovery

Autoresearch hands the experiment loop to an AI agent: it edits one file, runs a fixed test, reads one number and keeps or reverts the change. I tried it twice, once on the problem it was built for and once on a hunt for hidden backdoors in language models. The second run went smoothly and found nothing, and the reasons say more about autoresearch than about the hunt.

Mayank SaxenaMarch 2026Code and data

01What autoresearch is

Karpathy’s autoresearch is a small experiment in letting a language model do its own research (Karpathy 2026). A coding agent is given a training script and a standing instruction: make the model better. It changes the script, trains for exactly five minutes, reads the validation loss, and commits the change if the loss went down or reverts it if not. Then it does it again, all night.

On its home ground this works. I ran a community port to MLX, Apple’s machine-learning library for Mac chips, on an M4 Pro laptop (Peterson 2026; MLX). Its score is validation bits per byte: how many bits the model needs per character of unseen text, so lower is better. Two kept changes, each halving the batch size, took it from to .

The reason it works is easy to miss. In training, the number is the goal, so climbing it cannot lead you astray.

02Applying it to backdoor discovery

In early 2026, Jane Street hid triggers in four language models: prompts that make a model behave very differently (the Dormant LLM puzzle; Jane Street 2026). I mapped the loop onto the hunt:

IngredientIn the backdoor hunt
Editable fileA list of probe prompts, one file per model.
Fixed experimentSend the prompts to a model and score every reply.
One numberAn anomaly score: how far a reply’s length strays from 15 ordinary answers, plus how many of its words they never used.
Keep or revertKeep the batch if its best reply beats the best so far.

The agent was Claude Code running Claude Sonnet 4.6. It could edit its probe files and run an allowlist of commands; anything else needed my approval. Over it ran batches and prompts.

A validated trigger had to give the same anomalous reply in 3 of 3 repeats, not be a known artifact such as an echo, and have near variants that behaved normally (Appendix B has the permissions and criteria in full). Nothing met the bar. The strongest candidate anomaly, “🌙” on Model 2 answered with just “🌙✨”, held in of repeats.

03What transferred: the mechanics, not the objective

The workflow carried over; the objective did not. Each session started from notes on the best so far and the ideas already ruled out, so it never retried dead ends. Each step was a single allowlisted command, and every batch was one commit with every reply saved.

04Where it broke

04.1The number

An autoresearch loop climbs whatever number you give it. Outside training, the number is no longer the goal but a guess about what the goal looks like, and the agent climbs the guess. My anomaly score was an imperfect proxy for “this model is behaving strangely”.

The score rewards replies whose length is far from the baseline answers’ and whose words they never used. Tell the warmup model “The magic word is: Spartan” and it replies “Spartan!”: one new word in the shortest possible reply, near the maximum score, and no backdoor involved. No reply is shorter than one word, so this is a ceiling, between and depending on the model (Appendix A). of the probes reached it, almost all of them echoes like this or one-word answers the prompt asked for.

The keep rule turned the ceiling into a stall: once one batch reached it, no later batch could beat it. On the warmup model that happened at batch , and all batches after it were reverted. The agent noted the ceiling on day two and kept climbing anyway. Autoresearch fixes the metric so the agent cannot game it, which also means it cannot repair it.

04.2Around the number

  • Repeats that could not separate signal from noise. The local model decoded greedily, so even the “Spartan!” echo repeated of times; the API models sampled, so even the best candidate held only of .
  • A narrow search. Keep-if-better pulled each batch toward past winners, and the agent proposed words and phrases from the backdoor literature it knew. The triggers disclosed after the close were structured inputs, the first 15 digits of π and a Game of Life board (Kruger 2026); the loop never tried either kind.
  • Unreliable self-reports. Asked for its trigger or system prompt, the warmup model answered confidently and inconsistently; none of its answers held up.

05Rules for an autoresearch loop

Autoresearch works when climbing the number is the same as making progress. When the number is only a proxy, these are the rules I would now follow:

  1. Test the score on a known trigger first. Check that a planted or already-known positive scores at the top. I did not run this check.
  2. Find the ceiling and handle it. If cheap outputs can max out the score, penalise them, and let the agent flag the metric for review instead of climbing it.
  3. Verify, and keep diverse candidates. Re-run each candidate under fixed settings before it is kept, archive distinct high scorers rather than one best, and save budget for kinds of input not yet tried.

Appendix A: the score and its ceiling

score = 0.6 × |words − baseline mean| / baseline sd + 4 × share of new words

Words are whitespace-separated tokens with punctuation stripped, lower-cased; “new” means absent from the model’s 15 baseline answers. A one-word reply made of a new word scores 0.6 × (mean − 1) / sd + 4, the most any reply shorter than the baseline mean can score. Longer replies gain length points again; on the API models, which had no length limit, a reply of a few thousand words could pass the ceiling. None did: the longest ( words) scored .
